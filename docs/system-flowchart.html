1

系統總覽(現況)

實線是目前實際運行的路:上傳+內部資料集 → 解析 → 三大判別 → 加權裁決 → 輸出草稿 → Prototype 人工調整 → 最終輸出分「聚陽模式」與「通用模式(Stytrix Generator)」。左下虛線區是已驗證但尚未串接的外部 API。

2

使用流 — 目前實際的推論路徑

上傳後系統以內部資料集判斷、產出草稿,人在 Prototype 頁把關調整,最後依情境選擇輸出模式:聚陽模式或通用模式(Stytrix Generator)。每一筆修正都會被記錄餵回訓練。

輸出模式 A

聚陽模式

情境:聚陽內部日常使用。

輸出:對齊聚陽既有格式與流程 — 推薦做工、推薦尺寸表、PDF,銜接後續內部系統。

輸出模式 B

通用模式 Stytrix Generator

情境:不綁定聚陽格式的通用產生器,供其他客戶/對外情境使用。

輸出:通用格式的做工與規格輸出。

※ 兩種模式的欄位與版型細節,建議列入下次會議一併確認。

3

訓練流 — 標準答案怎麼建立、怎麼回流

從清理資料表開始,建立 Golden Sample 金標、定義標準答案,餵進模型訓練,再用 L1/L2 評分把關;未達標的部分由人工補充,修正結果回流成下一輪訓練資料,形成閉環。這條線是目前實際在做的整理與訓練工作。

4

三大判斷來源與加權裁決

流程圖不只畫資料流,也要畫「系統怎麼判斷」:三個判別來源各有擅長與現況準確率,加權裁決決定誰優先、誰補強、什麼情況交給人工。

圖像辨識

60%

判什麼:部位、口袋、門襟、剪接線等視覺項目

現況:模型準確率約六成,需持續訓練

做工翻譯(文字解析)

80%

判什麼:老師傅做工語句,依 Golden Sample 與規則庫解析

現況:整體準確率約八成

信心指數

90%

判什麼:用大數據比對補強,約九成可跑出

現況:在圖像或翻譯不確定時作為覆蓋依據

5

資料來源與缺口

目前實際在流程中的是內部整理資料集;四支外部 API 都已完成可用性驗證但尚未串接 — 何時正式接入,是要與 MIS 排時程的重點。

資料來源狀態已有目前缺口下一步/窗口
目前實際在流程中 — 內部資料集
KPAC 翻譯資料(匯出) 使用中 可用翻譯資料約 900+ 款 早期資料缺款號 評估補款號方式
做工登記簿/規則表 使用中 部位/機種/做工規則 持續整理中 隨訓練流逐輪補齊
Golden Sample 標準答案庫 建置中 部分金標 覆蓋率不足 訓練流核心資料,持續擴充(見第 3 節)
已驗證可用 · 尚未進流程 — 外部 API
MTM API 已驗證·未串接 已綁 NKCSO/SSO,可取 JSON JSON 欄位不完整 下週 review,與 Zack 確認缺欄位
KPAC/Judy 翻譯平台 API 已驗證·未串接 API 可呼叫 未接入流程 與 MIS 排定串接時程與權限
StyleTricks/MTM Patch 評估中 — 可補欄位待確認 評估作為補齊欄位的第二支 API
POM/TagPack 尺寸表 未結構化 多為 PDF 文件 缺結構化欄位 確認是否有 POM grading、tolerance 資料
